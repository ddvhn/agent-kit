# Setting up Patrol

Writing tests afterwards: `writing-patrol-tests`. Flavors themselves: `configuring-flutter-flavors`. Values below are placeholders (flavor `dev`, applicationId / bundle id `com.example.foo.dev`, `MainActivity` in `com.example.foo`); the project's real values go in `CLAUDE.md` → Project facts.

This replaces LeanCode's upstream `patrol-setup` skill in the kit: it covers Android, iOS, and web, puts `MainActivityTest` in `MainActivity`'s own package, keeps the MCP runner out of the app's dependencies, and proves the setup with the app's own harness instead of a widget-only test.

**Ask first** (one batch, with a recommended default): which flavor Patrol installs (the non-prod one), which platforms, whether to add the Patrol MCP, and whether CI should run the suite.

## 1. Dependencies

- CLI, once per machine (goes into the README setup steps): `dart pub global activate patrol_cli`. Keep `patrol_cli` and the `patrol` package on compatible versions (Patrol docs → compatibility table).
- `dev_dependencies` of the app that runs the tests: `patrol`, `mocktail`, and the SDK mock packages the harness needs (`firebase_auth_mocks` for Firebase Auth).
- `.gitignore`: `**/test_bundle.dart` (generated by the CLI), `.patrol.env`; web also `**/test-results/` and `**/playwright-report/`.

## 2. `patrol:` block (`pubspec.yaml`)

```yaml
patrol:
  app_name: Foo Dev                 # home-screen name of the installed flavor
  flavor: dev                   # the non-prod flavor; mobile only
  test_directory: patrol_test
  android:
    package_name: com.example.foo.dev   # that flavor's applicationId
  ios:
    bundle_id: com.example.foo.dev      # that flavor's bundle id
```

A web-only app needs `app_name` and `test_directory`. In a workspace with several apps, each app folder has its own block, and Patrol runs from that folder. Never point Patrol at the prod flavor.

## 3. Android

`android/app/build.gradle.kts`:

```kotlin
android {
    defaultConfig {
        testInstrumentationRunner = "pl.leancode.patrol.PatrolJUnitRunner"
        testInstrumentationRunnerArguments["clearPackageData"] = "true"
    }
    testOptions {
        execution = "ANDROIDX_TEST_ORCHESTRATOR"
    }
}

dependencies {
    androidTestUtil("androidx.test:orchestrator:1.5.1")
}
```

Groovy (`build.gradle`): `testInstrumentationRunner "pl.leancode.patrol.PatrolJUnitRunner"`, `testInstrumentationRunnerArguments clearPackageData: "true"`, `testOptions { execution "ANDROIDX_TEST_ORCHESTRATOR" }`, `androidTestUtil "androidx.test:orchestrator:1.5.1"`. The orchestrator with `clearPackageData` gives every test file a fresh app.

`android/app/src/androidTest/java/com/example/foo/MainActivityTest.java` — the `package` is `MainActivity`'s package (the folder `MainActivity` lives in), not a flavor applicationId:

```java
package com.example.foo;

import androidx.test.platform.app.InstrumentationRegistry;
import org.junit.Test;
import org.junit.runner.RunWith;
import org.junit.runners.Parameterized;
import org.junit.runners.Parameterized.Parameters;
import pl.leancode.patrol.PatrolJUnitRunner;

@RunWith(Parameterized.class)
public class MainActivityTest {
    @Parameters(name = "{0}")
    public static Object[] testCases() {
        PatrolJUnitRunner instrumentation =
            (PatrolJUnitRunner) InstrumentationRegistry.getInstrumentation();
        instrumentation.setUp(MainActivity.class);
        instrumentation.waitForPatrolAppService();
        return instrumentation.listDartTests();
    }

    public MainActivityTest(String dartTestName) {
        this.dartTestName = dartTestName;
    }

    private final String dartTestName;

    @Test
    public void runDartTest() {
        PatrolJUnitRunner instrumentation =
            (PatrolJUnitRunner) InstrumentationRegistry.getInstrumentation();
        instrumentation.runDartTest(dartTestName);
    }
}
```

- A permission whose native dialog no test exercises (camera for a QR scanner, for example) can be pre-granted at the start of `runDartTest`, before `runDartTest(dartTestName)`: on API 28+ `instrumentation.getUiAutomation().grantRuntimePermission(instrumentation.getTargetContext().getPackageName(), Manifest.permission.CAMERA)`.
- Emulator: wait until boot completes before running. If Patrol discovers 0 tests, try another system image.

## 4. iOS

1. Xcode → File → New → Target → **UI Testing Bundle** named `RunnerUITests`, language Objective-C, target to be tested `Runner`. Delete the generated test files and add `ios/RunnerUITests/RunnerUITests.m`:

   ```objc
   @import XCTest;
   @import patrol;
   @import ObjectiveC.runtime;

   PATROL_INTEGRATION_TEST_IOS_RUNNER(RunnerUITests)
   ```

2. Build settings of `RunnerUITests`: deployment target equal to `Runner`'s, bundle id `com.example.foo.dev.RunnerUITests`, `TEST_TARGET_NAME = Runner`, the same development team, and a build configuration for every flavor configuration (`Debug-dev`, `Release-dev`, `Profile-dev`, …).
3. Link Patrol into the target:
   - Swift Package Manager (the Flutter plugin package is in the project): add `FlutterGeneratedPluginSwiftPackage` to `RunnerUITests` → Frameworks and Libraries.
   - CocoaPods only: inside `target 'Runner'` in the `Podfile` add `target 'RunnerUITests' do inherit! :complete end`, then `pod install`.
4. Add `RunnerUITests` to the **Test** action of every flavor scheme (`dev`, `staging`, `prod`) and keep the schemes shared.
5. Boot a simulator before running.

## 5. Web

- Run from the app folder: `patrol test --device chrome` (one file: add `--target patrol_test/foo_test.dart`). No flavor on web. Chrome must be installed; Patrol drives it through Playwright and writes `test-results/` and `playwright-report/`.
- `System` stays empty; the harness pins the locale and clears persisted preferences.

## 6. Harness skeleton and first test

Prerequisites in the app (ask before changing app code beyond these):

- The app widget can be pumped without `main()` (`const Application()`), and startup work `main()` does before `runApp` is callable from the harness.
- `injectDataLayer` takes `skipSdkInit` once it sets up an SDK (no Firebase or other SDK setup in tests), and every I/O dependency is registered by its contract so the harness can replace it (`di` rule → Wiring).
- Widget keys live in a keys file per feature in the UI package, aggregated in `Keys` (`writing-patrol-tests` → Widget keys).

Create, following the templates in `writing-patrol-tests`:

```
patrol_test/
  test_app.dart                # testApp + MockDependencies
  mocks/mock_backend_api_client.dart
  mocks/mock_database.dart
  modules/module.dart  modules.dart  system.dart  app_module.dart
  guest_sees_sign_in_test.dart   # first test
```

First test: the signed-out launch reaches the first screen, with an empty API-client mock and a fresh database. It proves the DI replacements, the database lifecycle, keys, and native wiring at once. The skeleton's `MockDependencies` record holds only these three doubles; add fields when a test needs to drive another service:

```dart
void main() {
  testApp('shows the sign-in page to a guest', _mockDependencies, ($, modules, system) async {
    await modules.app.launch();
    await modules.signIn.waitUntilVisible();
  });
}

Future<MockDependencies> _mockDependencies() async => (
  apiClient: MockBackendApiClient(),
  database: mockDatabase(),
  firebaseAuth: MockFirebaseAuth(),
);
```

Run it on each platform: `patrol test --target patrol_test/guest_sees_sign_in_test.dart` with `--flavor dev` (mobile, unless the block sets it) or `--device chrome` (web).

## 7. Patrol MCP (optional)

Add it only if the user wants agents to run single tests through MCP. The runner is an isolated package so its dependencies never enter the app's pubspec or workspace resolution.

`tool/patrol_mcp/pubspec.yaml`:

```yaml
name: foo_patrol_mcp
description: Isolated patrol_mcp runner. Not part of the app workspace.
publish_to: none

environment:
  sdk: ^3.10.0   # the app's constraint

dependencies:
  patrol_mcp: ^0.2.0
```

`cd tool/patrol_mcp && dart pub get` (a README setup step). `.mcp.json`:

```json
{
  "mcpServers": {
    "patrol": {
      "command": "/bin/sh",
      "args": ["-c", "export PROJECT_ROOT=\"$PWD\" && cd tool/patrol_mcp && exec dart run patrol_mcp"],
      "env": { "PATROL_FLAGS": "", "SHOW_TERMINAL": "false" }
    }
  }
}
```

- `PROJECT_ROOT` is the folder with the `patrol:` block (`$PWD/apps/foo` in a workspace).
- `PATROL_FLAGS` takes `patrol develop` flags the block does not set: `--device chrome` on web, `--flavor dev` if the block has no flavor.
- Tools: `run` (`testFile`), `status`, `screenshot`, `native-tree`, `devices`, `quit`.

## 8. Commands and CI

- Gradle-driven repositories get a suite task per flavor (root `build.gradle`, inside the flavors loop):

  ```groovy
  tasks.register("integrationTest${flavor.capitalize()}", Exec) {
      commandLine("patrol", "test", "--flavor", flavor, "--target", "patrol_test")
  }
  ```

- CI (only if the user asked): a runner with a booted emulator or simulator (or Chrome) runs the suite command on the non-prod flavor, with no production secrets.

## 9. Record it

- `CLAUDE.md` → Project facts: Patrol folder, flavor, devices, the doubles and fakes, whether the MCP exists. Verification: the one-file and whole-suite commands.
- The repository's `.claude/rules/testing.md`: harness names, fixtures or presets, where fallbacks are registered, the keys aggregator path.
- README one-time setup: the Patrol CLI, and `dart pub get` in `tool/patrol_mcp` if added.

## Gotchas

| Symptom | Fix |
| --- | --- |
| `MainActivity` cannot be resolved | `MainActivityTest`'s `package` and folder must match `MainActivity`'s package |
| `patrol test` fails without `--flavor` | Set `flavor:` in the block or pass `--flavor` |
| App installs but tests never start on iOS | `RunnerUITests` missing from the flavor scheme's Test action, or not linked to Patrol |
| Android finds 0 tests | Try another emulator system image; boot fully before running |
| Test passes once, then state leaks | Orchestrator or `clearPackageData` missing; the harness must reset the service locator and delete the DB |
| Other failures | Patrol docs FAQ: https://patrol.leancode.co/documentation |
